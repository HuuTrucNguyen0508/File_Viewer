# File Viewer audit, 2026-10-31

## Scope and result

Read-only source audit of `/home/theadenkingof/Documents/Code/File_Viewer`, branch `feat/initial-app`, HEAD `5362edb`. Six actionable findings remain: four P1 resource-exhaustion issues and two P2 correctness issues. No fixes were applied.

Review covered entry points and permissions, detection, source and cache ownership, viewer dispatch, browser navigation, WebView/XML boundaries, document and data parsers, archive handling, native-viewer integration, Gradle/manifest configuration, tests, and verification tooling. README, PLAN, SUPPORT, and both phase reviews informed the review. Historical emulator results were not treated as current verification. Knowledge searches for `File_Viewer` and `File Viewer` found no relevant prior notes.

P1 means untrusted input can exhaust the viewer's heap or block its UI despite the existing limits. P2 means normal use can display incorrect or incomplete content. These are local availability and correctness findings, not demonstrated code execution or data exfiltration.

## Findings

### 1. P1: one deeply nested archive path exhausts memory on the UI thread

Evidence: [ArchiveTree.kt:21](../app/src/main/java/com/fileviewer/app/viewers/archive/ArchiveTree.kt#L21), especially lines 24–29; [ArchiveViewer.kt:78](../app/src/main/java/com/fileviewer/app/viewers/archive/ArchiveViewer.kt#L78).

Trigger: an archive with one entry named `("a/" repeated 16,000 times) + "x.txt"`. Its name is 32,005 characters, within a ZIP filename's representable byte length. It consumes only one of the 100,000 allowed entries and does not nest archives.

`ArchiveTree` copies and joins every prefix, then retains each full prefix in a node. Memory and work grow quadratically with path depth. Compose constructs the tree in `remember`, on the UI thread, outside the listing worker's error handling. The exact compiled constructor throws `OutOfMemoryError` with a 128 MB JVM heap. The UI cannot reliably reach Hex or Info when this happens.

Recommendation: bound path length, directory depth, and total implied nodes before tree construction. Build the bounded tree off main. Avoid copying every prefix and retaining full paths for all nodes.

### 2. P1: font name records amplify a small table into hundreds of megabytes

Evidence: [FontNames.kt:29](../app/src/main/java/com/fileviewer/app/viewers/misc/font/FontNames.kt#L29), especially lines 32–45 and 57; [FontInfo.kt:20](../app/src/main/java/com/fileviewer/app/viewers/misc/font/FontInfo.kt#L20); [FontViewer.kt:46](../app/src/main/java/com/fileviewer/app/viewers/misc/font/FontViewer.kt#L46).

Trigger: a 120,006-byte name table with 5,000 Windows Unicode name records referencing the same 60,000-byte string. The string storage follows the record array, and every offset and length passes the current checks. This is below the 1 MB input-table limit.

The parser decodes and retains a separate String for every record before selecting the handful of names actually displayed. Shared string ranges defeat the input-byte limit. Calling the exact compiled `NameTable.parse` with this table throws `OutOfMemoryError` at line 44 under a 128 MB heap. This runs before the platform font loader, so platform rejection does not protect the parser. The surrounding `runCatching` can report some failures, but it does not prevent process-wide heap pressure.

Recommendation: select the preferred record for each displayed name before decoding. Bound the total decoded characters and individual name length, and avoid decoding duplicate ranges repeatedly.

### 3. P1: ZIP metadata loads before the archive entry cap applies

Evidence: [ZipInspector.kt:16](../app/src/main/java/com/fileviewer/app/detect/ZipInspector.kt#L16); [ArchiveAccess.kt:130](../app/src/main/java/com/fileviewer/app/source/ArchiveAccess.kt#L130); [DocPackage.kt:74](../app/src/main/java/com/fileviewer/app/viewers/documents/DocPackage.kt#L74).

Trigger: a roughly 25 MB ZIP containing 300,000 empty entries. `ZipInspector.refine` constructs Commons Compress's `ZipFile` before doing its 16 marker lookups. Construction reads and retains the central-directory entries. Archive listing and document-package checks likewise count entries only after constructing `ZipFile`.

The compiled `ZipInspector.refine` exhausts a 128 MB JVM heap on this fixture, before any lookup budget can protect it. The same fixture completes under 256 MB, confirming that this reproduction depends on available heap. Larger directories remain unbounded. Detection happens before the viewer switcher is available. Catching an allocation failure afterwards does not enforce the promised resource cap.

Recommendation: reject excessive entry counts and metadata bytes before constructing an eager ZIP index, using a bounded central-directory inspection. Apply the same gate to detection, listing, entry opening, and document packages. Include ZIP64 and filename/extra-field totals in that bound.

### 4. P1: Markdown's byte cap does not bound its syntax tree or rendered output

Evidence: [MarkdownHtml.kt:30](../app/src/main/java/com/fileviewer/app/viewers/data/markdown/MarkdownHtml.kt#L30), especially line 33; [MarkdownViewer.kt:27](../app/src/main/java/com/fileviewer/app/viewers/data/markdown/MarkdownViewer.kt#L27); [Limits.kt:40](../app/src/main/java/com/fileviewer/app/source/Limits.kt#L40).

Trigger: a Markdown file consisting of `- a\n` repeated 400,000 times, only 1,600,000 input bytes, below the 32 MB data-text cap.

`parser.parse(body)` builds the complete CommonMark tree, then the renderer builds the complete HTML string. There is no node or output budget. The exact compiled `MarkdownHtml.render` throws `OutOfMemoryError` during list parsing with a 128 MB heap. Its coroutine has no failure handler, so it cannot offer the normal source fallback on failure. Running on `Dispatchers.Default` also supplies no cooperative cancellation checks during the parser call.

Recommendation: bound Markdown complexity before building the tree, or parse incrementally with explicit node and output budgets. Fall back to source when a budget is reached, and give cancellation and parse failures an explicit owner. A bound checked only after parsing is too late.

### 5. P2: reopening a changed content URI can reuse obsolete bytes

Evidence: [ContentUriSource.kt:22](../app/src/main/java/com/fileviewer/app/source/ContentUriSource.kt#L22); [Materialize.kt:25](../app/src/main/java/com/fileviewer/app/source/Materialize.kt#L25); [RealFile.kt:25](../app/src/main/java/com/fileviewer/app/viewers/misc/RealFile.kt#L25).

Trigger: open a stream-only content URI, return to the browser, edit that document in its provider, and reopen the same URI while the File Viewer process remains alive. Fonts/APKs also copy content URIs through `FileCopyOf` even when a descriptor exists.

The source key contains only the URI, and materialization returns an existing cached copy without checking current metadata or bytes. A temporary JVM probe used two stream-only sources with the same URI-shaped key. The first supplied `old`, the second supplied `new`; materialization returned `old` both times. An actual Android provider was not exercised. Source inspection confirms that `ContentUriSource` uses this key policy. Derived archive-entry keys inherit the same stale parent identity.

Recommendation: scope cached copies to an opening session, or invalidate them when reopening. Metadata can help but is insufficient when a provider omits timestamps or changes content without changing length. Preserve reuse within a single opening without assuming the URI identifies an immutable revision.

### 6. P2: Hex silently makes the tail of large local files unreachable

Evidence: [HexViewer.kt:73](../app/src/main/java/com/fileviewer/app/viewers/hex/HexViewer.kt#L73) and [HexViewer.kt:105](../app/src/main/java/com/fileviewer/app/viewers/hex/HexViewer.kt#L105).

Trigger: open a local file larger than about 16 GiB when the screen selects 8-byte rows, or 32 GiB with 16-byte rows. Local seekable files bypass the stream-copy size limit.

The list clamps the number of rows to `Int.MAX_VALUE`. Go to offset clamps every target to that same list, so offsets in the remaining file silently land at the last representable row. Neither a truncation notice nor a second window makes the tail accessible. This contradicts SUPPORT's any-size Hex claim. The finding follows directly from row arithmetic and source control flow, without allocating or reading a large fixture. No device reproduction was attempted.

Recommendation: use a movable file-offset window with bounded list indices, and map go-to-offset into that window. Until that exists, disclose the precise limit instead of silently clamping.

- N1: bound distinct extra-field ids per header at 64, in central and local headers. A 62,842-byte ZIP with 60 entries sharing 15,000 distinct fields took about 31 seconds in detection; it is now refused in preflight. Distinct ids are counted because zipalign's zero padding parses as thousands of id-0 fields. Repeated ids stay cheap in the library: 279 entries sharing 15,000 identical fields detected in 77 ms under `-Xmx128m`, and the worst case under the cap, 16,384 entries with 64 distinct fields, took 311 ms.

S1 deliberately keeps eager local-header parsing. Commons Compress 1.28.0 source (`/tmp/file-viewer-audit/compress-sources.jar`, `ZipFile.java`) shows `setIgnoreLocalFileHeader(true)` skips `resolveLocalFileHeaderData` and consequently Unicode-extra name/comment recovery. `getEntry` still works with central-decoded names; `getInputStream` computes offsets on demand through `getDataOffset`/`setDataOffset`; ZIP64 sizes and offsets are read from central extras. This app uses recovered names for listing and lookup, so losing recovery would change behavior. No app code directly reads local-only extras. A regression fixture verifies CP437 names/comments recovered through Unicode extras, ZIP64 sizes, lookup and entry contents. The preflight accounts for ZIP64 local offsets and prefix correction, and counts shared extras repeatedly to match the library's allocations.

The Markdown budget is 360,000 work units: 4 per line, 32 more for a block-starting line, 1 per markup/autolink punctuation character, and 4 per column per table body row. Container depth is limited to 64 at the line prefix, including ordered list markers. The separate line-token cap was removed; HTML still stops at 8,000,000 characters while appending. Tables require a header and delimiter with matching column counts. CommonMark 0.30.1 also treats pipe-free nonblank continuation lines as table rows, verified by a 100-column fixture reaching the library's 1,000,000-cell guard without preflight; these real padded rows are charged too. The regression test retains that protection. Stray pipes outside tables have no multiplication term.
